# README 契约：几十个仓库怎么做到"结构统一、内容各自不同"

> 起因（2026-10-26）：小胆宝的 README 收到一条意见——"先回答这是什么、谁适合用、主要功能、解决什么痛点，然后才是功能展现"。
> 拿同族五个仓库一比，问题不是这一个仓库的：
>
> | 仓库 | 行数 | 第二个二级标题 | 首屏有没有回答"这是什么" |
> |---|---|---|---|
> | liver-cancer-workbench | 122 | 疾病概要 | 只有一行 tagline，然后直接进疾病定义 |
> | lung-cancer-workbench | 139 | Git开发快照 · 2026-10-20 | 开头是开发快照，读者要读 6 行才知道这是什么 |
> | ovarian-workbench | 118 | Git开发快照 · 2026-10-20 | 同上 |
> | thyroid-workbench | 102 | 疾病概要 | 同 liver |
> | bladder-workbench | 108 | 疾病概要 | 同 liver |
>
> 也就是说：**九个仓库（抽样五个）没有一个是"读者视角"开头的**。它们都从"疾病概要"或"开发快照"开始——
> 前者是给已经知道自己要什么的人看的背景资料，后者是给维护者看的。而第一次点进来的人（患者、家属、想提 PR 的开发者）
> 在前 30 秒要判断的是另外四件事。

## 结论先说：统一靠"骨架 + 闸"，不靠"写文档时自觉"

一句话讲完的办法：**把"读者要问的四个问题"固化成六节固定骨架，用脚本当闸，项目只填内容。**

三层分离，谁也不越界：

| 层 | 谁定 | 内容 | 能不能改 |
|---|---|---|---|
| **骨架层** | 家族（本文件 + `templates/README-family.md`） | 六节标题、顺序、每节最少要说清什么、边界句位置 | **禁改**。改了 `check-readme` 就红 |
| **项目层** | 各仓库维护者 | 这是什么 / 谁适合用 / 主要功能 / 痛点表 / 截图 / 首版短板 | 必填，且必须具体到本癌种 |
| **资料层** | 各仓库维护者 | 疾病概要（定义 / 指南 / 治疗全景 / 趋势）、开发与本地验收、致谢 | 可长可短，可增减小节；只要排在六节之后 |

"统一"只统一骨架层，"契合各自项目"全在项目层与资料层。这样既不逼所有人写成同一篇，也不会再有仓库把"疾病概要"顶在最前面。

## 六节骨架（顺序即读者的决策链）

| 顺序 | 小节 | 读者在这一秒问什么 | 判断标准 |
|---|---|---|---|
| 1 | `## 这是什么` | 这玩意儿是啥？ | 三到五句 + 一张"不是"表；一句话说清形态（记录工具，不是产品） |
| 2 | `## 谁适合用` | 关我事吗？ | 适合的人用"他的处境"描述，不用医学词；**必须写"不太适合"** |
| 3 | `## 主要功能` | 能干什么？ | 表格 6–10 行，动词开头，每行能对上后面一张截图 |
| 4 | `## 能解决哪些患者痛点` | 治好我哪个痛？ | 表格：痛点原话 ｜ 现在的难受 ｜ 本台的处理 ｜ 本台不做 ｜ 核实状态 |
| 5 | `## 功能展现` | 长什么样？ | 真实截图按页分组，不许只放 logo |
| 6 | `## 第一版不完美…` | 敢用吗？我能帮上什么？ | 列已知短板 + PR 最小形态 + 会被拒的 PR + 致谢 |
| 之后 | `## 疾病概要` … | （已经不问了） | 背景资料后置；四小节结构沿用原样 |

**为什么"痛点表"必须带"本台不做"和"核实状态"两列**：家族所有项目的红线是"不做判断"。
痛点表如果只写"我们能解决 X"，读起来就是疗效承诺；把"本台不做"和"这条假设还没核实"并排写出来，
才是这个项目真正想给人的预期——**边界本身就是功能**。

## 机器闸：`scripts/check-readme.mjs`（R1–R7）

```bash
node scripts/check-readme.mjs .              # 人读
node scripts/check-readme.mjs . --json       # 批量扫几十个仓库时用
```

| 编号 | 检查 | 为什么 |
|---|---|---|
| R1 | 恰好一个 H1；**第一个 H2 必须是「这是什么」** | 这一条就把"疾病概要开头"堵死了 |
| R2 | 六节都在、顺序递增、各有 ≥80–120 字实质内容 | 只有标题不算；只有一张图也不算（计长时先剥 img/link） |
| R3 | 痛点节是表格且 ≥5 行（表头 + 分隔 + 3 条） | 防样板化 |
| R4 | 前 60 行出现「不替代 / 不构成医疗建议」 | 边界句必须在首屏，不是文末免责 |
| R5 | 功能展现节含 `docs/screenshots/` 真实图 | 与 `check-readme-shots.mjs` 互补：一个管"有没有图"，一个管"图在不在正确的节里" |
| R6 | 首版节提到 PR；提到社区/致谢（warn） | 把"欢迎贡献"落成可执行的入口 |
| R7 | 疾病概要 / 当前状态 / 开发与本地验收 / 致谢（warn） | 资料层的完整性，不拦 |

已接入 `npm run check`（`check:readme`）。现有 `check-readme-shots.mjs` 继续管截图与目录 1:1，两者不重叠。

**闸不替代评审**：字数下限只能拦住空节，拦不住空话。人工看一条就够——每一节里有没有**本癌种专有的名词**
（Bismuth-Corlette、FGFR2、引流量 ml/24h、TSH 抑制…）。没有专有名词的段落，换成任何一个癌种都成立，那就是要退的。

## 几十个仓库怎么落地（四步，按成本从低到高）

**第 1 步：模板进脚手架（一次投入，长期收益）**
把 `templates/README-family.md` 推进 `dsh-wb-cli`，新仓库生成即合规，不产生新的历史债。
这一步只能由能改脚手架的人做——**在这之前，先让各仓库自己 `cp templates/README-family.md README.md` 再填**。

**第 2 步：批量体检（半小时，只读）**
各仓库先拿到这份脚本（同一个文件，无需改），然后一次性扫：

```bash
cd ~/Downloads
for d in *-workbench; do
  [ -f "$d/README.md" ] || continue
  node "$d/scripts/check-readme.mjs" "$d" --json | node -e '
    let s="";process.stdin.on("data",c=>s+=c).on("end",()=>{
      const r=JSON.parse(s);if(!r.ok)console.log(r.repo, "→", r.fails.map(f=>f.code).join(","))
    })'
done
```

输出就是改造清单：`R1,R2a,R2b…` 的集合基本每个仓库都一样，所以能批量处理。

**第 3 步：按仓库改造（人力主要花在这）**
每个仓库一次，顺序**建议按 R1 + R2 的缺项数从少到多**，先做 2–3 个试点（挑 README 最完整、截图最全的），
把成品当范例再推广。没截图的仓库不要硬凑"功能展现"——先跑 `npm run probe:proto` 或如实写"暂无截图，见 docs/…"。

**第 4 步：把闸变成发布前提**
`npm run release:check` 里已含 `check`（含 `check:readme`）。发布/投稿前必须绿。
另外建议在每个仓库的 `docs/RELEASE.md`「家族一致性」一行旁边加一格 README 契约：`R1–R7 全绿 · 2026-10-26`。

## 附：可批量投喂的改写提示词

> 单个仓库改造时，把下面这段连同 `README.md`、`docs/PATIENT-FLOW.md`（或等价的患者流程文档）一起给 agent。
> 关键是**不许它编**：所有痛点必须能回到已有文档，回不去的标"未经核实"。

```text
你是这个癌种工作台的文档编辑。请按家族 README 骨架重写 README.md：

1. 保留原有二级标题的文字与顺序不变的部分：疾病概要（四小节）、开发与本地验收、HTML先行与数据演进、致谢。
   它们全部移到六节之后。
2. 在最前面新增六节，标题文字固定：
   ## 这是什么 / ## 谁适合用 / ## 主要功能 / ## 能解决哪些患者痛点 / ## 功能展现（N 屏 / M 张） / ## 第一版不完美，需要懂这个病的人一起改
3. 内容来源只用仓库已有文件：docs/PATIENT-FLOW.md（用户假设 U1–U6）、docs/SPEC.md、docs/FEATURE-INVENTORY.csv、
   prototypes/ 与 docs/screenshots/。**不得新增任何未在仓库中出现的事实、数字或指南条文。**
4. 痛点表五列：痛点（患者那一刻的原话）｜现在的难受在哪｜本台的处理｜本台不做｜核实状态。
   核实状态照抄 PATIENT-FLOW.md 的标注（"未经访谈核实" / "n=1 非正式输入（日期）"），不许改写成"已验证"。
5. 主功能表的每一行都要能对上「功能展现」里的一张截图；对不上的删掉那行，不要留空头功能。
6. 首屏（前 60 行）必须出现一句边界声明：不诊断、不推荐方案、不替代医生。
7. 不删任何一张已引用的截图；原有 <img> 标签原样保留。
8. 改完自己跑：node scripts/check-readme.mjs . && node scripts/check-readme-shots.mjs .
   两条都绿才算完成；红了按输出的"改法"继续改，不要改脚本。
```

## 不做什么

- **不做"标准化模板填空"**：六个标题固定，但每节内容必须是本癌种自己的话。安全检查：把项目名换成另一个癌种，如果整段还成立，就是没写具体。
- **不追求所有仓库长得一样**：资料层（疾病概要、致谢、开发章节）本来就该不同，本契约不管那部分。
- **不用同一个版本号管所有仓库**：契约版本写在本文与 `templates/README-family.md` 顶部，各仓库 README 不必写契约版本。
