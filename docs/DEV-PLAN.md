# 开发计划（DEV-PLAN）

> 与 `docs/TASKS.md` 的分工：TASKS 记**当前状态与交接**，本文件记**怎么排、按什么顺序、每步怎么算做完**。
> 版本：v0.1.0 · 更新 2026-10-26 · 闸口：G1 ✅ / G2 🟡（8/56）/ G3 ⬜

## 一、总原则

1. **闸口先行**：G2 逐条确认 → G3 冻结 schema → 才写 `src/`。本文件里的 T02 之后全部标「未获准开工」，不是「未排期」。
2. **原型即合同**：`prototypes/v0.2/` 是布局、文案、二级导航、交互的默认实现合同，parity 目标 >98%。
3. **口径可执行**：M1–M13 不能只写在文档里。能在检查里判的进 `scripts/check-medical-rules.mjs` 与 `test/`，判不了的写进验收人读项。
4. **一次一个业务单元**：按完整页面成组实现与检查，不逐样式跑全链路，也不全站写完才第一次验证。

## 三、P4 内部的实施顺序（先重后轻）

1. **labs**（9 条功能，M2/M3/M8/M10 全落在这里）——最容易被"顺手解读"污染，先把边界立住。
2. **trials**（12 条，M13）——匹配引擎要抽成纯函数并单测，不能留在渲染函数里。
3. **dash**（4 条，M9）+ **jaundice/drain**（7 条，M4）——提醒位与观察项的写法最容易越界。
4. **treat**（6 条，M7）+ **type**（4 条，M5/M6）。
5. **chart**（3 条，C1–C12）——一图秀断言多，放在数据稳定之后。
6. **imaging / care / settings / 跨页**（11 条）——依赖少，收尾。

## 四、每个单元的完成定义（DoD）

- 代码：`npm run check` 绿（语法 / 版本 / 单测 / schema / 9 条口径 / 文案红线 / 包结构）。
- 行为：该页每个 ACC 条目能被指出来（截图或实际点击路径），parity 表打勾。
- 数据：读模型来自统一事实源，不为页面单独建表；派生值不落库。
- 文案：禁用词零命中；解释层带机构 + 版本 + 页码，缺一显示「未引入」。
- 失败面：零条 / 单条 / 多条 / 缺字段 / 错误状态五种都有界面。
- 交接：`docs/TASKS.md` 状态更新，坑写进 `docs/LESSONS.md`。

## 五、风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 逐页走查拖长 | 56 条按页确认，容易停在中间 | 每页固定「截图 + ACC 对照 + 我发现的问题」，一次只问一页；确认一条记一条 |
| 口径漂移 | 实现时凭记忆写"稳定/好转" | `check-medical-rules.mjs` 与 `check-wording.mjs` 双网，字面违规直接 fail |
| 数据模型返工 | 按 Tab 建表 | schema 以实体/证据/版本为核心；G3 前允许整体改写，G3 后只增不改 + 新迁移 |
| 合成数据被当真 | `DEMO-` 试验被读成真实试验 | 每个列表页固定声明"合成数据"；`verified_on` 为空不得显示在招 |
| 版本分散 | 改 VERSION 忘了同步 | `build:version --check` 在 `npm run check` 里，四处不一致直接 fail |
